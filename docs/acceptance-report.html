01综述

问题定义

Stats NZ 每季度发布《Overseas Trade Indexes》，其中每一行是一个"序列 × 季度"的观测， 包含单位、状态、商品分组、价格类型等元数据，以及一个数值指标 Data_value。 本项目的任务是：给定某个序列的元数据和季度，预测它在该季度的指数数值。

这是一个回归问题，而非分类。业务上的意义是：当某个序列的当期数值尚未公布或缺失时， 可以用同等元数据的其他序列来估计它的合理区间，用于早期趋势判断。

六个关键设计决策

决策备选方案选择理由
用 RandomForestRegressor 线性回归 / 梯度提升 数据里绝大多数是类别型元数据，树模型天然处理非线性交互；线性基线的 R² 只有 0.47，明显欠拟合
只保留 UNITS == "Index" 的行 混合所有单位一起训练 不同单位的数值量纲完全不同（指数 vs 纽币 vs 百分比）。混在一起时模型会去学"单位"而不是"规律"，同一批特征会对应几百和几百万两种目标
模型产物提交进 Git 用 DVC 管 / 从 MLflow Registry 拉 CI 里没有训练数据（DVC 需要 Azure 凭据），也无法访问 MLflow 服务。把 15 MB 产物随仓库走，CI 才能构建出真正能服务的镜像
MLflow 用 sqlite:///mlflow.db 默认的 ./mlruns 文件后端 MLflow 3.x 已将文件后端标记为维护模式，mlflow ui 会直接拒绝启动
训练依赖与运行时依赖分离 一个 requirements.txt 全装 MLflow 及其传递依赖约 200 MB，推理时完全不需要。分离后镜像从约 400 MB 降到 181 MB
CD 用 build-arg 而非 COPY .env 把生成的 .env 打进镜像 镜像层是不可变的，打进 .env 等于把配置（以及真实项目中的凭据）永久固化。改用构建参数，机制相同但无残留
一句话概括： 这套项目的核心不是"把模型跑通"，而是让每次预测都能回答"它来自哪份数据、哪次训练、哪份代码、哪个环境"。 后面所有章节都在证明这句话。

def _estimator_name(pipeline) -> str:
    """返回具体估计器的类名，而非包装器的。

    type(pipeline).__name__ 永远是 "Pipeline"，对调用方毫无信息量。
    有用的名字是最后一个步骤的类名，这样健康检查才能报出
    RandomForestRegressor。
    """
    steps = getattr(pipeline, "named_steps", None)
    if steps:
        last = list(steps.values())[-1]
        return type(last).__name__
    return type(pipeline).__name__


class ModelHolder:
    """持有已拟合的 sklearn 管线及其溯源元数据。"""

    def load(self, model_path=DEFAULT_MODEL_PATH,
             summary_path=DEFAULT_SUMMARY_PATH) -> None:
        """从磁盘加载管线。

        抛出带可操作提示的 FileNotFoundError，而不是让裸的 joblib
        异常逃逸：产物缺失是运维问题，不是服务 bug。
        """
        path = Path(model_path)
        if not path.exists():
            raise FileNotFoundError(
                f"model artifact not found at {path}. "
                "Run `python -m ml.train` to create it."
            )

        self._pipeline = joblib.load(path)
        self._model_type = _estimator_name(self._pipeline)
        self._data_version = None

        if summary_path is not None:
            summary = Path(summary_path)
            if summary.exists():
                meta = json.loads(summary.read_text(encoding="utf-8"))
                self._model_type = meta.get("model_type") or self._model_type
                self._data_version = meta.get("data_version")

    def predict(self, frame: pd.DataFrame) -> float:
        """为单行特征表打分并返回预测值。"""
        if self._pipeline is None:
            raise ModelNotLoadedError("model is not loaded")

        if len(frame) != 1:
            raise ValueError(f"expected exactly 1 row, got {len(frame)}")

        return float(self._pipeline.predict(frame)[0])

def load_raw(path: str | Path) -> pd.DataFrame:
    """读原始 CSV，所有列保持文本，转换由我们控制。

    也阻止它为 Period（形如 YYYY.MM 的文本）猜测数值类型。
    """
    return pd.read_csv(path, dtype=str, keep_default_na=False, na_values=[""])


def normalize_units(series: pd.Series) -> pd.Series:
    """让 UNITS 一致：源数据混用了 Index 和 index。"""
    return series.str.strip().str.title()


def clean(df: pd.DataFrame) -> pd.DataFrame:
    """应用基础清洗规则并返回新表。

    步骤：
        1. 重命名拼错的 MAGNTUDE 列
        2. 丢弃标识列与近乎为空的列
        3. 归一 UNITS 的大小写
        4. 把 Data_value 转数值并丢弃没有目标的行使
        5. 用 Unknown 填补剩余的类别空缺

    本函数不按单位过滤；select_target_units 单独做这件事，
    使该步骤显式且可测试。
    """
    out = df.copy()
    out = out.rename(columns=RENAME_COLUMNS)
    out = out.drop(columns=[c for c in LEAKY_COLUMNS + DROP_COLUMNS if c in out.columns])

    if "UNITS" in out.columns:
        out["UNITS"] = normalize_units(out["UNITS"])

    # 没有目标值的行对监督学习毫无用处
    out[TARGET] = pd.to_numeric(out[TARGET], errors="coerce")
    out = out.dropna(subset=[TARGET])

    for column in CATEGORICAL_FEATURES:
        if column in out.columns:
            out[column] = out[column].astype("string").fillna(UNKNOWN)
            out[column] = out[column].str.strip()
            out[column] = out[column].replace("", UNKNOWN)

    return out.reset_index(drop=True)


def select_target_units(df: pd.DataFrame, units: str = TARGET_UNITS) -> pd.DataFrame:
    """只保留 UNITS 等于 units 的行，并丢掉该列。

    过滤之后 UNITS 是常量，不携带任何信息。
    """
    out = df[df["UNITS"] == units].copy()
    out = out.drop(columns=[c for c in ("UNITS",) if c in out.columns])
    return out.reset_index(drop=True)


def drop_constant_columns(df, features=None, min_unique: int = 2):
    """丢弃不携带信号的列（唯一值少于 min_unique）。

    v2 过滤到 Index 单位后 MAGNITUDE 塌缩成单一值，
    留着它只会多出一个无用的 one-hot 列。
    """
    features = list(features if features is not None else FEATURE_COLUMNS)
    kept = [c for c in features if c in df.columns and df[c].nunique() >= min_unique]
    dropped = [c for c in features if c in df.columns and c not in kept]
    out = df.drop(columns=dropped) if dropped else df.copy()
    return out, kept


def add_time_features(df: pd.DataFrame) -> pd.DataFrame:
    """把 Period（YYYY.MM）拆成整数 year 与 month。

    无法解析的行得到 NaN，由调用方丢弃。源数据里没有这样的行，
    但这道防线能避免 API 在坏输入上崩溃。
    """
    out = df.copy()
    period = out["Period"].astype("string").str.strip()
    parts = period.str.extract(r"^(?P<year>\d{4})\.(?P<month>\d{2})$")
    out["year"] = pd.to_numeric(parts["year"], errors="coerce")
    out["month"] = pd.to_numeric(parts["month"], errors="coerce")
    return out

def run_experiment(name, model, X_train, X_test, y_train, y_test,
                   params, categoricals, commit, data_version, data_hash):
    """拟合一个模型、评估它，并把一切记进 MLflow。

    返回拟合好的管线供调用方导出用于服务，以及留出集指标。
    """
    pipeline = Pipeline(steps=[("prep", build_preprocessor(categoricals)),
                               ("model", model)])

    with mlflow.start_run(run_name=name):
        # ① 代码版本
        mlflow.log_param("git_commit", commit)
        # ② 数据集版本（来自 .dvc 指针的 md5）
        mlflow.log_param("data_version", data_version)
        mlflow.log_param("data_dvc_hash", data_hash)
        # ③ 超参数（含数据规模，便于判断训练条件）
        mlflow.log_param("train_rows", len(X_train))
        mlflow.log_param("test_rows", len(X_test))
        for key, value in params.items():
            mlflow.log_param(key, value)

        pipeline.fit(X_train, y_train)
        predictions = pipeline.predict(X_test)
        # ④ 指标
        metrics = evaluate(y_test, predictions)
        mlflow.log_metrics(metrics)

        return pipeline, metrics

def dvc_hash(pointer_path: str) -> str:
    """读取 DVC 指针里的 md5，作为数据集版本标识。

    该哈希由文件内容算出，数据一变它就变，
    这正是手册所说的 "DVC dataset version ID"。

    DVC 指针形如::
        outs:
        - md5: 42171ec985af1d3aed38f4d6f497030b
          size: 23324132
          path: raw_dataset.csv

    md5 行以 YAML 列表标记 "- " 开头，匹配前要先剥掉它。
    """
    path = Path(pointer_path)
    if not path.exists():
        return "unknown"
    for line in path.read_text(encoding="utf-8").splitlines():
        stripped = line.strip()
        if stripped.startswith("- "):
            stripped = stripped[2:].strip()
        if stripped.startswith("md5:"):
            return stripped.split("md5:", 1)[1].strip()
    return "unknown"

为什么用 RandomForest，而不是线性回归或梯度提升？

数据里绝大多数特征（STATUS、Subject、Group、四个 Series_title）都是类别型的。 经过 one-hot 编码后维度很高，且这些类别之间存在复杂的交互效应。三点理由：

  • 线性模型明显欠拟合：基线 R² 只有 0.4689，说明目标与特征的关系高度非线性，线性假设不成立。
  • 树模型天然处理类别交互：每棵树在随机子空间上划分，能捕捉"某个 Group 下的某个 Series_title_2 才有的规律"，不需要手工构造交互项。
  • 不需要特征缩放：year/month 与 one-hot 列的量纲差异不会影响树的分裂点选择。

没选梯度提升，是因为 RF 在默认参数下更稳、对过拟合更宽容，且训练时间与调参成本更低——在本项目的数据规模（6 万训练样本）上，RF 已经达到 0.91 的 R²，继续追求边际收益不划算。

R² = 0.9085 可信吗？是否存在过拟合？

为什么要滤掉 UNITS != "Index" 的行？

因为不同单位的 Data_value 量纲完全不同：

  • Index —— 指数，典型值几百到几千
  • Dollars —— 金额，典型值几百万
  • Percent —— 百分比，典型值个位数

如果混在一起训练，模型会用同一套特征去预测几百万和个位数两种目标——它学到的不是"规律"，而是"这一行是哪种单位"。而 UNITS 本身又不是输入特征（过滤后被删掉了），所以模型无从分辨，只能给出一个折中的、对谁都不准的预测。

过滤后剩 77,337 行，目标值落在同一量纲，模型才可能学到真正的规律。

为什么最后要删掉 MAGNITUDE 列？

这是过滤带来的连带结果，不是独立决定。

MAGNITUDE 原本标记数值的量级（例如"千"、"百万"）。一旦只保留 UNITS == "Index" 的行，几乎所有 Index 值的量级标记都变成同一个值（0），这一列就塌缩成常量。

为什么删 Series_reference 和 Series_title_5？

DVC 和 Git 各自负责什么？为什么不都用 Git？

职责切分：

  • Git 管代码与指针。一个 .dvc 文件只有 6 行（md5 + size + path），体积可忽略。
  • DVC 管数据本体。23 MB 的原始 CSV 和 16 MB 的清洗 CSV 存在 Azure Blob 上。

不都放 Git 的原因：Git 的存储模型是"每个版本完整保存一份"，二进制大文件每次改动都会让仓库体积翻倍，且 clone 会变得极慢。即使后来有 Git LFS，它也缺乏"数据版本与代码版本绑定"的语义。

DVC 的价值在于：.dvc 指针里的 md5 由文件内容算出，改一个字节就变，无法伪造。这就把"数据版本"变成了一个可校验的标识符，能直接写进 MLflow 的 data_dvc_hash 参数。

为什么用 lifespan 而不是 @app.on_event("startup")？

@app.on_event 在 FastAPI 中已被标记为弃用（deprecated），官方推荐用 lifespan 上下文管理器。

除了"不过时"，lifespan 的结构优势是启动与关闭的代码在同一个函数里：yield 之前是启动逻辑，之后是清理逻辑。这样资源的获取与释放不会被拆散在两个装饰器里，读代码时能一眼看出配对关系。

本项目目前只在 yield 前加载模型，没有清理逻辑；但如果将来要加连接池或后台任务，lifespan 是唯一正确的挂载点。

lifespan 里为什么捕获 FileNotFoundError，而不让进程崩溃？

这是可观测性优先于快速失败的取舍。

如果容器启动时 model.joblib 缺失：

  • 崩溃式：进程退出 → 容器重启 → 再退出，形成重启循环。在 docker logs 里只能看到反复的一小段堆栈，很难判断根因。
  • 降级式（本项目的做法）：进程活着，/health 返回 model_loaded: false，/predict 返回 503。运维可以 curl /health 立刻看出"服务在，但模型没加载"，再去查日志里的 model artifact missing: …。

关键区别：503 的语义是"我能响应，但暂时不能服务"，这比 connection refused 更准确地描述了故障状态。生产环境里健康检查也能据此把该实例从负载均衡摘掉，而不是让整个容器反复重启。

predict() 里为什么要检查 len(frame) != 1？

这是一个防御性断言，把"意外"变成"立刻报错"。

为什么 random_state 固定为 42？

为了让结果可复现，这是 MLOps 的基本要求。

不确定性来自三处：train_test_split 的切分、RandomForest 的 bootstrap 抽样与特征子采样。三处都用 RANDOM_STATE = 42 固定后：

  • 任何人 clone 仓库、dvc pull、python -m ml.train，都能得到完全相同的指标（RMSE 240.0274 等）。
  • MLflow 里两个 run 的指标可以直接对比——如果种子不同，0.9085 与 0.9101 的差异可能只是随机波动，无法判断改动是否真的有效。

代价是失去了"多次运行看方差"的信息，但对课程项目来说可复现性更重要。

compress=3 是什么？为什么不用 compress=9？

joblib.dump(..., compress=N) 中 N 是 zlib 压缩级别（0=不压缩，9=最大压缩）。

级别体积加载耗时适用

314.6 MB可接受本项目：进 Git、进镜像

选 3 是因为它在"体积缩小 3 倍"和"解压速度"之间取得平衡。模型只在启动时加载一次，所以解压耗时只影响冷启动；但体积直接影响 Git 仓库和镜像大小，这是持续成本。

skops_trusted_types 是干什么的？为什么必须传？

MLflow 3.x 改用 skops 而非 pickle 来序列化 sklearn 模型，因为 pickle 反序列化会执行任意代码，不安全。

skops 默认只信任一个白名单类型集合。RandomForestRegressor 内部的 sklearn.tree._tree.Tree 不在默认白名单里，于是 log_model 报错：

显式传入 skops_trusted_types=["sklearn.tree._tree.Tree"] 等于声明"我知道这个类型是安全的"。因为我们是在自己的进程内刚训练出来的模型，不是在加载外部文件，所以这个信任是合理的。

extra="forbid" 和 str_strip_whitespace 各解决什么问题？

extra="forbid"：pydantic 默认忽略多余字段。这意味着客户端把 year 错拼成 yaer 时，请求会"成功"，但 year 用了默认值或报缺失——错误信息指向缺失字段，而不是拼写错误，用户很难定位。

设为 forbid 后，多余字段直接 422，并明确指出 yaer 是多余的。这符合"快速失败"原则。

str_strip_whitespace=True：自动裁剪字符串首尾空格，使 " FINAL " 与 "FINAL" 等价。否则空格会进入 one-hot 编码，变成一个训练集里从未出现过的新类别，被 handle_unknown="ignore" 静默处理为零贡献——用户不会收到任何错误，但预测质量下降了。

为什么把公共 Logger 的配置写成 if not logger.handlers？

为了防止重复挂载 handler 导致同一条日志被打印多次。

模块级代码在 import 时执行。在测试场景里，如果模块被重新导入（例如 importlib.reload，或某些测试框架的隔离机制），模块级代码会再跑一遍。如果没有 if not logger.handlers 这层判断，就会再 addHandler 一次，于是同一条 model loaded 会输出两遍、三遍。

这是一个典型的"幂等初始化"写法。

如果 API 收到训练时从未见过的类别，会怎样？

会正常返回预测，不会报错。这是刻意设计的行为。

链路：OneHotEncoder(handle_unknown="ignore") 把未知类别编码为全零向量 → 该类别对预测零贡献 → 预测值更接近整体均值。

R² = 0.9085 会不会太高了，像是数据泄漏？

这个怀疑很合理，我核查过三处最可能的泄漏源：

  1. Series_reference 已删除 —— 它是每行的唯一 ID，保留会导致"查表"式记忆。LEAKY_COLUMNS = ["Series_reference"] 就是为它设的。
  2. 目标列未混入特征 —— 特征列表是 NUMERIC_FEATURES + CATEGORICAL_FEATURES，Data_value 不在其中。load_dataset 里也显式 feature_frame = frame[NUMERIC + categoricals]。
  3. 没有用未来信息 —— 特征是"季度 + 序列元数据"，都是该观测自身已有的属性，不包含其他季度的数值。

那为什么还这么高？因为这是一个"同一序列在不同季度上重复出现"的数据集。同一组元数据（Subject + Group + Series_title_1..4）会在多个季度反复出现，模型实际上在学"这个序列的典型水平"，而季度间的波动相对较小。所以 R² 高是合理的。

真正的隐患不是泄漏，而是评估方式：随机切分会让同一序列的不同季度同时出现在训练集和测试集里，模型"见过"这个序列。更严格的做法是按序列分组切分（GroupKFold），看模型对全新序列的泛化能力。我预计那样 R² 会明显下降——这才是诚实的泛化估计。

这个分析我写在了 ml/README_experiments.md §6 的局限里。

符合手册的部分：手册原文明确写的是 "uses GitHub secrets … to create a staging .env file, then build the staging Docker image"——要求止于构建镜像。这部分我完整实现了，且两个环境确实用了各自的 Secrets。

不符合"真实部署"的部分：镜像只存在于 runner 的临时磁盘上，工作流结束后就没了。没有推送到 registry，也没有在服务器上启动容器。

为什么这样选择：推送需要 registry 凭据（GHCR 需要 GITHUB_TOKEN 的 packages: write 权限），启动需要目标主机。这些超出课程范围，而且引入真实凭据会增加"提交了不该提交的东西"的风险。

但我把补齐路径写清楚了：DEPLOYMENT.md §7 列出了完整方案——docker/login-action + build-push-action 推送、拉取重启、/health 健康门禁、失败回滚、运行时密钥注入。所以这不是"没想到"，而是"有意限定范围并写明下一步"。

这个项目如果交给别人接手，最大的障碍是什么？

SAS 令牌的"体外循环"。

.dvc/config.local 被 gitignore 是正确的安全实践，但代价是：新人 clone 仓库后，dvc pull 会直接失败，而错误信息不会告诉他"你需要向某人要一个 SAS 令牌"。

当前 README 提到了这一点，但不够醒目。更好的做法：

  • 提供 .dvc/config.local.example（占位符形式），并在 README 显眼位置说明"首次 clone 需复制此文件并填入令牌"
  • 或者用 dvc remote modify --local 的文档化脚本

第二障碍是环境变量在两个地方：本地靠手工 -e APP_ENV=local，CD 靠 GitHub Environment Secrets。两者没有单一事实来源。现实中应该用 .env.example + pydantic-settings 统一。

三层证据：

  3. 全仓库扫描：scripts/verify_project.py 遍历每一个被跟踪的文本文件，用正则 sp=racwdl|sig=[A-Za-z0-9%]{20,} 搜索 SAS 令牌特征，结果为空。

这里踩过一个坑：最初我用 git log -p --all 做扫描，结果因为 subprocess 用 GBK 解码抛 UnicodeDecodeError，异常在子线程被吞，检查假通过。修复后才真正有效——而且修复后的版本立刻抓到了一个真实命中（脚本自身的正则字面量），证明它确实在工作。

为什么不用 GitHub Actions 的 matrix 同时跑两个环境？

因为两个环境不该同时构建。

matrix 会把 staging 和 production 的构建并行化，但它们的触发条件截然不同：staging 只在合并到 staging 分支时构建，production 只在合并到 main 时构建。任何一次合并最多只应构建一个环境的镜像。

用两个独立 job + if: github.ref == … 的效果是：一个执行、一个显示为 skipped。这既符合语义（我确实只想构建一个），也让 Actions 页面上的意图一目了然——你能直接看到"production 被跳过了"，而 matrix 里看不到这种对比。

另一个原因：matrix 的值必须能在编译期枚举，而 environment 是 job 级属性，无法在 matrix 里动态绑定不同的 GitHub Environment。这是 Actions 的机制限制。

如果 CI 里 96 个测试要跑很久，怎么办？

当前实测整个 CI 约 57 秒，其中测试本身只占很小一部分——瓶颈是 pip install 和 docker build，不是测试。所以优化方向应该按收益排序：

手段收益成本
setup-python 的 cache: pip（已启用）依赖缓存，重复构建省约 20 秒已做
Docker 层缓存（buildx + cache-from/to: gha）CI 的 docker build 从约 36 秒降到几秒需要 docker/setup-buildx-action
测试并行化（pytest-xdist）96 个测试本就不慢，收益有限增加依赖

我的判断：57 秒对一个 PR 检查来说完全可以接受，加 buildx 缓存是下一个最有价值的优化，但当前不是瓶颈。过早优化会引入不必要的复杂度。
